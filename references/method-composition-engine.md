# 多维方法组合引擎

## 目标

面对新稿件时，不检索“哪条参考片像它”，也不复述原片时间码。系统只读当前稿件中的判断结构，激活一组相互协作的导演方法，让多个维度共同服务同一个画面因果。

```text
新稿件
-> 判断图谱
-> 语义信号
-> 主导演程序
-> 辅助程序
-> 原子动作职责图
-> 冲突消解
-> 五阶段效果链
-> 镜头与微时间拍
```

方法知识分为四层，而不是一份原则清单：24 类信号负责识别认知运算，24 套结构程序与 18 条融合规则负责搭建状态骨架，48 套执行配方负责题材、媒介、世界和效果落地，96 条原子动作负责具体对象的状态变化。编辑真源见 [method-trigger-lattice.yaml](method-trigger-lattice.yaml)、[director-method-recipes.json](director-method-recipes.json) 和 [director-move-catalog.yaml](director-move-catalog.yaml)；[method-runtime-contract.json](method-runtime-contract.json) 是触发矩阵确定性编译出的运行时只读镜像，不得手改。

```text
24 SG 语义信号
-> 1 个主 DP + 0–3 个辅助 DP
-> 1 个主 DR + 0–2 个叠加 DR
-> 按语义完整激活原子动作，不设数量配额
-> 5 阶段效果链
```

## 一、先读“关系”，不要读“关键词”

关键词只能提示候选，不能直接决定画面。真正触发方法的是句子在论证中承担的运算：

| 表面词 | 可能的真实运算 | 判断方法 |
|---|---|---|
| “增长” | 绝对数量变大、份额变化、速度变化或口号 | 找单位、基线、时间窗和比较对象 |
| “AI” | 产品身份、内部机制、抽象能力或品牌语境 | 找核心判断到底要证明存在、功能、机制还是价值 |
| “因为” | 因果、相关、推测或叙事顺序 | 找是否有可说明的传输机制和结果 |
| “第一” | 排名、时间先后、市场份额或品牌主张 | 找评判口径和证据责任 |
| “改变” | 属性替换、结构重组、状态转移或情绪转折 | 找保持不变的身份和真正变化的变量 |

先把每段改写成一个不可再拆的关系式：

```text
主体 A 在条件 C 下，因为机制 M，从状态 S0 变为 S1，
相对基线 B 产生结果 R；证据 E 的责任是证明/解释/比较其中哪一环。
```

写不出关系式时，不进入画面设计；继续拆段或标出未知项。

## 二、建立判断图谱

每段先提取以下节点：

```yaml
claim: 唯一核心判断
subject: 主体
object: 被作用对象或比较对象
initial_state: 变化前
operator: 比较/因果/组成/流程/转化/证明/分类/时间演化
mechanism: 发生变化的路径或规则
result_state: 变化后
baseline: 比较基线
evidence_burden: existence/source/relation/mechanism/comparison/mood
uncertainty: 不得被画面包装成确定事实的缺口
```

这里的 `operator` 决定主信号；题材、媒介、数据、品牌和情绪通常只是次信号。

## 三、信号激活

### 主信号

每段恰好一个主信号。选择标准不是“出现次数最多”，而是删掉它后核心判断是否仍能成立。主信号回答观众必须完成的认知动作，例如：

- 看出差异：`SG03 公平比较`。
- 理解为什么：`SG05 因果关系`。
- 看清怎么运作：`SG06 内部机制`。
- 相信它发生过：`SG09 引用与原始材料` 或 `SG10 真实存在证明`。
- 理解价值从何而来：`SG18 成本与价值`。

### 次信号

次信号最多四个，只能强化以下责任之一：

```text
evidence | world | comparison | text/data | emotion | media handoff
```

若一个次信号要求新的主体、新的视觉世界和新的结论，它不是次信号，而是应该拆出的下一段。

### 信号强度

每个信号用 0–3 分评估：

| 分数 | 含义 |
|---:|---|
| 0 | 只是题材联想，没有结构责任 |
| 1 | 能增强语境，但删除后判断不变 |
| 2 | 承担证据、比较、世界或结果的一部分 |
| 3 | 决定核心认知运算，必须成为主信号 |

只允许一个 3 分。出现两个 3 分时先拆段，不要强行把两段塞进 15 秒。

## 四、选择主程序和辅助程序

主程序决定五阶段状态骨架；辅助程序不能再造一条骨架。

例如一段同时包含“产品能力 + 内部机制 + 数字提升”：

```text
主程序 DP09 产品英雄机制结果
辅助 DP06 隐形机制剖面：只插入 development/turn
辅助 DP08 基线差值结论：只在 payoff 的结果槽给出数值
```

错误做法是先播产品广告、再切一段科普、再切一张数据海报。正确做法是同一产品始终在英雄坐标，剖面解释它为何改变，结果数字在同一坐标中落下。

### 主程序评分

候选程序每项 0–2 分：

| 维度 | 问题 |
|---|---|
| 语义同构 | 程序状态骨架是否与判断运算相同？ |
| 主体连续 | 核心主体能否贯穿 opening 到 landing？ |
| 证据责任 | 证明和解释是否各有载体？ |
| 单动作可执行 | 每阶段能否压成一个主动作？ |
| 15 秒闭合 | 能否在时长内完成初态、变化、结果和落点？ |
| H3 稳定性 | 是否避免脆弱小字、多人复杂表演和无锚媒介跳切？ |

总分低于 9 分不得成为主程序。并列时选择主体连续成本更低、事实风险更小的一项。

### 执行配方预编译

DP 只说明状态如何走，DR 配方继续回答“用什么证据、哪个世界、什么媒介、怎样运动”。优先把已经检测到的信号直接交给路由器；信号桥会自动推导每个信号的主特征与候选执行特征：

```bash
python3 scripts/compose_method_stack.py \
  --signals SG14,SG06,SG10 \
  --primary-signal SG14
```

只有上游已经提供更精确的题材或媒介判断时，才用 `--features PRODUCT,MECHANISM,LIVE_ACTION,SPEC --primary PRODUCT` 显式增补。每个已检测信号的主特征必须保留；主特征必须来自主信号；主程序必须属于主信号候选，且每个次信号至少被一个已选程序承接。这样“检测到了”不可能在后续悄悄失效。

路由器按同一输入稳定返回：

- 一个主程序、覆盖全部信号的最小辅助程序集和全部适用融合规则；上下文可增加有明确 binding 的辅助程序，但不能绕过确定性最低集合。
- 一个主配方，决定执行主轴和持久世界。
- 零到两个叠加配方，只补充未覆盖的语义或媒介责任。
- 去重动作必须完整覆盖当前语义义务并包含 `N/C/M/L/Q`，不以条数或维度数凑配额。
- 单世界锁、密度/高能冲突、真实证据/重建冲突、文字和运动并发说明。
- 媒介政策、失败信号、未入选候选，避免只报告“选了什么”。

路由结果是预编译候选，不是免思考答案，但也不能被悄悄丢弃。先把原始 `resolved_move_ids` 原样写入 `router_move_ids`，再为每个语境增删写结构化差分：

```yaml
move_adaptations:
  - operation: remove
    move_id: C02
    constraint: continuity
    reason: 当前主体必须保持单窗口坐标，不能切成双栏比较
  - operation: add
    move_id: C01
    constraint: continuity
    reason: 锁定主窗口的位置、比例和正面轴线
```

允许的约束来源只有 `source_semantics | available_media | duration_budget | fact_boundary | continuity | delivery_format`。从路由集合重放全部增删后必须恰好等于 `selected_moves`；否则配方正确也视为方法栈失真。

### 不可被适配删除的骨架

- 主信号的 `forced_moves` 全部进入最终动作。
- 主程序的完整 `spine` 全部进入最终动作。
- 每个辅助程序至少贡献两条自身 spine 动作。
- 主配方至少贡献四条 `required_moves`；每个叠加配方至少贡献两条。
- 每个检测信号至少触发一条最终动作，不允许“识别了但没有画面责任”。

适用的 `FR01–FR18` 必须逐条写入 `fusion_bindings`，并声明 `activated_by + stages + move_ids + implementation + combined_effect`；其中动作必须同时来自主程序和辅助程序 spine，不能只写规则 ID 冒充融合落地。主/辅程序和主/叠配方分别用 binding 声明 `activated_by + stages + move_ids + responsibility`；辅助方法最多进入两个阶段。五条 `stage_bindings` 必须按 opening、development、turn、payoff、landing 排列，全部动作只能归属一个阶段，opening 和 landing 必须由主程序收束。

## 五、把原子动作变成职责图

原子动作不是越少越好或越多越好，也不是时间轴事件清单。每条必须获得一个主职责：

```text
spine        决定判断的状态顺序
world        决定所有元素存在于哪里
composition  决定主体、证据和结果的坐标
evidence     决定什么画面能证明什么
text         决定文字、数据、单位和阅读顺序
motion       决定状态如何改变和反馈
transition   决定镜头/媒介如何交接
continuity   决定什么必须保留给下一拍/下一段
guardrail    拒绝伪事实、不可读、身份漂移和特效抢戏
```

每条动作必须写：

```yaml
move_id: M05
role: motion
triggered_by: [SG05, SG06]
contribution: 热量只沿已建立的材料表面从输入端传播到释放端
interacts_with: [N04, C04, L04]
```

`interacts_with` 说明它不是孤立效果：`N04` 提供因果顺序，`C04` 保留空间坐标，`L04` 保存已成立状态。没有协作对象的动作通常只是装饰。

## 六、冲突消解

多方法组合时，先处理六类常见冲突：

### 1. 世界冲突

纸面档案、技术观察台、产品舞台、地图和数据工作区不能在同一短段平权并列。选一个主世界；其他媒介进入固定窗口，或通过同一形状/动作短暂接力。

### 2. 主体冲突

品牌、产品、人物、数字和机制不能同时成为英雄主体。核心判断指向谁，谁占第一阅读；其余降为证据、标签或结果。

### 3. 动作冲突

同一时间拍只能一个主动作。相机运动、对象形变、粒子传播、文字飞入若同时发生，保留能推进判断的那个；其余延后、减弱或删除。

### 4. 证据与解释冲突

真实材料负责“它存在/发生”，MG 负责“关系和机制”。不能让生成画面冒充证据，也不能用无法读清的原始材料承担复杂解释。

### 5. 文字与画面冲突

当对象变化已经表达结论，文字只做短印章；当必须核对原文或数据，画面为文字让出稳定阅读区。不要让大字重复旁白并遮住变化。

### 6. 节奏冲突

高密度机制、关系和数据优先稳镜头微更新；活动包装才允许高能变奏。不能把广告节奏机械移植到解释段。

每段至少写一条 `collision_resolution`，说明哪两条方法发生竞争、最终谁负责什么以及为何。

## 七、五阶段效果链

每个段落必须闭合为一个效果链，而不是元素列表：

### Opening

建立核心主体、初态、空间规则和唯一视觉问题。观众应在两秒内知道看哪里，但不必已经知道答案。

### Development

输入、证据、局部或比较对象进入。只添加理解主动作所必需的元素；每个新增对象都有来源和槽位。

### Turn

发生唯一关键变化：链路建立、剖面打开、数据越过基线、对象重组、风险到达阈值或操作产生结果。

### Payoff

让变化成为可判断结果。数字带单位和基线，关系带方向和确定性，产品能力回到真实使用状态。

### Landing

画面制动并稳定 0.8–2 秒；留下短结论、已成立状态和下一段可继承锚。Landing 不是 Logo 自动出现，而是判断真正闭合。

## 八、时长压缩

方法不绑定原片时间码，只按当前段落预算伸缩：

| 时长 | 结构 |
|---|---|
| 4–7 秒 | Opening 与 Development 合并；Turn 一个动作；Payoff 与 Landing 合并；1–2 镜、3–5 微拍 |
| 8–11 秒 | 五阶段齐全但每阶段只一个状态；2–3 镜、4–7 微拍 |
| 12–15 秒 | 允许一个辅助程序进入 Development/Turn；3–5 镜、5–9 微拍 |

辅助程序数量不是越多越好。4–7 秒通常不超过一个辅助程序，8–11 秒不超过两个，12–15 秒最多三个。

## 九、放弃方法同样重要

每段至少记录两个 `discarded_methods`，理由必须具体：

- 因为没有原始材料，放弃证据全貌局部回环。
- 因为比较口径不存在，放弃基线差值程序。
- 因为产品身份必须稳定，放弃全屏抽象媒介跳转。
- 因为 8 秒不足以回装，放弃完整多层剖面，改用单路径高亮。

不能写“效果不好”“不适合”这类不可审计理由。

## 十、完成判定

暂停任一微时间拍，必须能回答：

1. 当前主信号是什么？
2. 主程序正处于哪个阶段？
3. 当前唯一主动作是谁做了什么改变？
4. 哪些辅助方法在服务它，而不是抢夺它？
5. 这个状态继承了什么，又要交给下一拍什么？
6. 删除任何一个视觉元素，会损失哪条信息？

若第 4 或第 6 个问题答不出来，说明方法只是叠加效果，应删除或重新分配职责。

交付前执行：

```bash
python3 scripts/build_method_runtime_contract.py --check
python3 scripts/compose_method_stack.py --exhaustive-test
```

前者证明 YAML 编辑真源与 JSON 运行时镜像完全一致；后者穷举一个主信号加零至四个次信号的 261672 个请求：一至四信号全部可路由，五信号中 161191 个可路由，51329 个因超过三个辅助程序的认知容量而被明确要求拆段或降级次信号；同时验证 48 个配方结构与 48 个可达配方路由。少量示例自测不能代替这两道门禁。
